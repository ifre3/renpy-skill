# 译文润色方法（可选策略）

> 适用场景：`game/tl/<lang>/` 已有初翻（autotranslate.py 管线或 AI 直接翻译均可），需要二次提质。
> AI 根据用户预算、文本量、质量要求**自行选择或组合**下列策略，不必询问；默认推荐策略一（局部润色档），用户明确要求全文提质或预算充足时才上策略二/三。

## 选型速查

| 策略 | 机制 | Token 成本 | 适用 |
|------|------|-----------|------|
| **策略零：校对档（非润色）** | `direct_polish.py` 机械改写（半角/重复标点、连续的的、被动"将会"、如果…的话等），不调大模型 | 0 | 还没 API 密钥；或想先零成本清洗明显翻译腔。**归类：校对工具**（与 `tl_check` / `screen_quality` 同族），不属于润色——它只修机械硬伤，不碰语义、语气与文风 |
| **策略一：母语流畅档（默认）** | 双角色两阶段 + **略读全文 + 罗列章节核心作辅助信息**；标准 = **目标语言母语者读得流畅**，**无文学性要求** | 局部档 ≈ 初翻的 25%~40%；全文档 ≈ 2~2.5 倍初翻 | 用户要"母语级流畅"（本文档默认档；按 §9 执行） |
| **策略一B：低扰动审稿档** | 双角色两阶段（原策略一）：通读场景块，默认"大部分不改"，只修读着别扭的行 | 局部档 ≈ 初翻的 25%~40%；全文档 ≈ 1.7~2 倍初翻 | 已有初翻、只想局部提质；或用户明确不要大动 |
| **策略二**：LinguaGacha 风格前置 | 翻译时挂风格预设/自定义文风指令 | 0 额外（本就要翻） | 还没翻 / 愿意重翻 |
| **策略二B**：LinguaGacha Agent 审校 | agent 按指定范围逐条润改 | 按指定范围计 | 不想写脚本、范围可控 |

## 策略一：母语流畅档（用户指定：母语级流畅，无文学性规定）

> 质量标准：**目标语言母语者读得流畅**——读起来像母语者写的，不追求文采。
> 与策略一B（低扰动审稿）的区别：一B 默认「大部分不改、只修别扭行」；本档**允许更主动的
> 改写**（语序重组、增删连接词、拆分长句），只要读着通顺自然——但底线不变：
> **禁止增删剧情信息、结构守恒、术语一致、仍只做一轮**。
> 必要时可**略读全文 + 罗列章节核心**作辅助信息（见下），这是本档与一B 的流程差异。

### 流程（§9）

1. **校对前置（零 token）**：策略零（`direct_polish.py`）+ `tl_check` + `screen_quality`
   先清机械硬伤与硬性质问题——母语流畅档只处理语义/语气/衔接层，别让 AI 把精力花在标点上。
2. **略读全文建立语境**：润色前让 AI 略读全文（超长项目读每章开头+结尾+随机抽样，目标
   约 5~10% 体量），建立人物、地点、术语、关系、整体语气的全局印象；产出辅助信息文件
   落 `<项目根>/.cache/polish/context.md`。
3. **罗列章节核心**：把全文按章节/场景列出**章节核心**（该章主线、关键情节、涉及人物、
   专名/伏笔、语气基调），每章 2~4 条要点；作为批次提示词前置的「辅助信息」，保证批内
   术语与全局一致、衔接不串戏。
4. **场景块润色**：沿用 `plan_batches.py` 连续剧本块（§7 规范：不截断长句、按场景合并相邻
   场景），但 prompt 判据从「大部分不改」改为「**以母语者读得流畅为准：读着别扭/不自然/
   不像母语者会说的话就改，通顺的保持原样**」。允许改写幅度更大，但：不增删剧情信息、
   保护 `{tag}` / `[expression]` / `%%` / 转义、对照原文注释核语义、术语查 `context.md`
   的章节核心。**该判据已内置 `plan_batches.py` 的 `render_prompt` 默认模板**
   （2026-10-27 升级；context.md 存在时自动带「全局上下文」段进 prompt；低扰动档
   策略一B 需要时把模板「标准」段手改为「大部分保持原样」）。
5. **仍只输出改动行 + 结构守恒门 + 只做一轮**（「越润越差」实测不变；辅助信息的作用是
   让第一轮更准，不是增加轮数）。`merge_polish.py` 剔除「改了等于没改」的行。
6. **回填 + 终检**：`autotranslate.py apply --overwrite` → 重跑 `tl_check` / `fmtlint`
   （E012 引号奇偶）/ `check_typography.py` 确认 0 异常 → 每批随机抽 10 行自查（发现误区即回写本档）。

### 实测参考（辅助信息的收益方向）

- Dissonance 0.14 实测：连续场景段中位数仅 1 条、最长 223 条——单看一批没有全局语境；
  略读 + 章节核心正是补这个缺口的低成本手段。
- §7 实测：表格化/截断会让 AI 退化成机翻矫正——本档依然要求连续剧本块；辅助信息是
  **叠加**，不是替代。

## 策略一B：低扰动审稿档（实测工作流）

来源：18 万字游戏对白实战（见文末来源①）。关键实测数据：初稿修改率约 75%（200 行改 150+），抽查 99% 的修改为正向改善；**润色只做一轮**——让润色者对自己再润一遍，好坏改动五五开，越润越差。

流程：

1. **切批**：按对话行分批（**约 150 句/批**，实测见「批次大小实测」节：200 偏大、
   100~150 更佳，成本优先可 200），一次只给润色者 2~3 批；批次过大会明显掉质量、
   术语不一致增多。切批与提示词生成已脚本化，见下方 5b 的 `plan_batches.py`。
2. **翻译者角色出初稿**：`autotranslate.py translate` 结果或 AI 直接翻译均可；初稿本来就会"一看就不行"，属正常现象，润色者第一遍会做大量优秀修改。
3. **审稿角色**（新会话/独立上下文，不与翻译者混用）prompt 要点：
   - **按连续剧本通读**，不是逐行矫正。喂给它的必须是「场景标题 + 说话人 + 完整原译对照」的剧本块，表格化、截断长句都会让它退化成机翻矫正（见下方 §7 实测）
   - **核心原则：大部分句子是好的，保持原样。** 只有确实读着别扭（语序生硬、词不达意、语气不符、前后衔接不上）才改，拿不准就不改
   - 禁止增删剧情信息；对照 tl 原文注释核对语义；保护 `{tag}`、`[expression]`、`%%`、转义符
   - **只输出改动过的行**（`file:line → 新译文`），判断为「不用改」的句子不进 JSON——这既省 token，也落实「只润一轮」
4. **术语一致性**：润色前先读项目根目录 `翻译结果.md` 的"专有名词"章；批次间把新术语回写进去（相当于实战文章里"让 Claude 自己做笔记"）。润色者改了很多人名/专名时会挤占其注意力，文风润色效果随之下降——此时拆小批或先统一术语。
5. **diff 回读**：初稿与润色稿逐行 diff，生成"行号｜原译文｜润色后"对照表供逐行接受/拒绝（VSCode diff 或脚本均可）。预期整行自动接受率约 60%，其余人工微调；被拒的行可选择性再丢给 AI 重润一次。
6. **记录**：重大意译写入 `翻译结果.md` 的"意译与润色"章。

回填沿用 `scripts/translate/autotranslate.py apply` 的安全规则（.bak + 原子替换、标签/插值结构校验、`--overwrite` 才覆盖非空译文）。

## 策略一的可执行管线（脚本级，实测）

上文是流程逻辑；落地时用以下脚本组合，全程不需要新写回填代码：

### 1. 枚举条目

`autotranslate.py scan <tl_dir> --skip-same` 输出的条目结构即回填 JSON 的结构：
`{"file": 相对tl_dir的路径, "line": tl文件内行号, "type": "tb/on/cd", "orig": 原文, "char": 角色变量(cd才有), "trans": 译文}`。
润色场景把 `trans` 填当前译文、改后填润色稿，`file`/`line`/`orig` 原样保留。

### 2. 回填

```
python autotranslate.py apply <tl_dir> --input .cache/polish_batch01.json --overwrite --dry-run   # 先预览
python autotranslate.py apply <tl_dir> --input .cache/polish_batch01.json --overwrite             # 实写（自动 .bak）
```

`--overwrite` 是必须的（润色覆盖非空译文）；默认 `--dry-run` 先跑一遍核对 SKIP 数。安全网：`line` 处的原文注释必须与 `orig` 完全一致才落笔，不一致/标签结构损坏自动跳过——所以**批次 JSON 里必须带准确的 file+line+orig**，不能只给新旧译文对。

### 3. 批次状态

润色跨多个会话/多天时，在 `<项目根>/.cache/polish_state.json` 维护批次状态（已完成批次号、每批 file 范围与行数、待重润行列表），避免重复润色。68k 行级项目不要指望一轮跑完。批次 JSON 与状态账本都放 `.cache/`（统一落盘约定见 [translation_workflow.md](translation_workflow.md) 2.5 第 1 步）——临时目录会被清空，账本一丢就等于从头重润。跨会话续跑契约（读账本 → 复查 → 从 `next` 继续 → `decisions` 不重问）以 [translation_workflow.md](translation_workflow.md) 第 0 节为唯一出处。

**回滚单元 = 批次 JSON 本身**：`batch_NNN.json` 的条目里存的是 plan 时点的**润色前译文**（`trans` 字段），某一轮回填后发现改坏了，不需要额外的快照机制——把该批 JSON 的 `trans`（旧值）与 fixes 里的新值对调、重放 `apply --overwrite` 即可还原该批，逐批回滚互不牵连。这也是「批次锚点必须齐全」的另一半理由。

### 4. 本地筛行规则（局部润色档的"可疑行"定义）

零 token 先跑：`tl_check.py`（崩溃/显示级先修）→ `check_duplicate_translations.py`（同句异译=术语漂移）→ `check_untranslated.py`（空译文/new==old）。再跑两个现成筛行器（polish/ 下，零 token）：

- `screen_suspicious.py`：翻译腔可疑行（连续多个"的"、`被` 字被动直译、`是否/如果…的话` 高频词、单句超长无标点；规则在顶部 RULES 增删）。**注意默认 `--min-score 2` 仍会漏掉只命中一条低权重规则的行**——专项排查夹生词时降阈值。
- `screen_quality.py`：硬性质可疑行（外文残留夹生词、假名残片、半角标点、相似度漏翻；已内置单字母/大写缩写/免翻短语豁免，详见 polish/README.md）。

筛出来的行按 file 分组进批次；两组输出锚点结构相同，可合并处理。

### 5. 原子化工具族（已内置：`scripts/polish/`）

上述管线已拆成单一职责小工具，用法与实测注意（strings 冲突、名字框机制、原版标签 bug 假阳性、裸 `%`）详见 `scripts/polish/README.md`：`extract_say.py`（全量条目+锚点）→ `screen_suspicious.py`（翻译腔筛行）+ `screen_quality.py`（硬性质筛行，规则经验移植自 LinguaGacha）→ `../names/apply_glossary_body.py`（术语表批量替换）或 `unify_name_translations.py`（人名统一）→ `merge_polish.py`（AI 只写 `file:line → 新译文`，锚点自动补齐；合并时过**结构守恒门**：拿润色稿与润色前译文比对标签/插值/`%` 格式符/换行数，对不上的条目直接剔除，规则取自 AiNiee 润色阶段的 ResponseChecker）→ `autotranslate.py apply --overwrite` 回填。

### 5b. 切批 / 提示词 / 账本：`plan_batches.py`（2026-10-11 新增）

上面第 1 步的「切批」与策略一流程第 3 步的「装上下文」此前只在文档里有原则性描述，没有脚本产出。现在由 `scripts/polish/plan_batches.py` 一次遍历做完，门面子命令 `polish`：

```
python scripts/renpy-tools-cli.py polish \
    --pool entries.json --tl <tl目录> \
    --candidates candidates.json quality_candidates.json \
    --batch-size 200 -o <项目根>/.cache/polish/
```

产出三样，都落 `-o`，**不碰 tl 文件**：`batch_NNN.json`（锚点齐全，可直接进 `merge_polish` / `apply --overwrite`）、`batch_NNN.prompt.md`（本批角色表 + 禁改清单 + 上一批已定术语 + 待润条目表）、`polish_state.json`（批次号 / file 范围 / 行数 / consumed）。

**为什么按「场景段合并」而不是「每场景一批」**（Dissonance 0.14 实测）：tl 里 44,409 个 `translate` 块去掉 8 位哈希后是 2,129 个场景名，但**连续**同场景段平均只有约 12 条、最长 223 条——按场景切会切出 3,659 批，比不切还糟。工具的做法是**以场景为边界、按 200 条上限合并相邻场景**：一段连续对白不会被劈成两半，同角色语气连贯；只有单场景超过上限才按条切，并标 `split: true` 提示 AI 保持术语一致。

**账本语义**：跑完一批把该批在 `polish_state.json` 里标 `consumed=true` 再跑下一批；重跑时已消费的批不再产出（落实「润色只做一轮」），未消费的批会被重排（条目集合可能随筛行结果变化）。账本不会因重跑而膨胀——这是实现时踩过的坑，已由 `test_polish_batches.py` 钉住。

### 6. 种子驱动探查（方法论吸收自 LinguaGacha item-review 审校技能）

来源：LinguaGacha `builtin/skills/translation/references/item-review.md`（2026-10 摘录自其 main 分支）。核心思想：**润色/校对不是一轮线性扫描，而是自启发循环**——每轮从上一轮的发现里提炼可检索的"种子"（特征模式/具体线索），用种子定位下一批调查目标，直到种子耗尽；至少 3 轮。落地到 Ren'Py 汉化：

1. **种子来源**：初始种子 = 两个筛行器的命中 + 用户 complaint；每轮探查后提炼新种子（发现"每日"漏译 → 全库检索 `毎日`；发现某角色译名漂移 → 检索该角色全部别名；发现某类 `{tag}` 被误翻 → 检索同类结构）。
2. **探查方向**（其原文归纳）：扩展同类（从单个错误提取特征找相似行）、核验差异（同词异译是否符合各自语境）、追查关联（术语/别名确认后复核受影响条目）。
3. **警告判断重点**：每类筛行命中不直接改，先核验再动笔——外文残留→查局部漏翻还是刻意保留（人名/拟声）；相似度→查是否漏翻还是翻译腔重写；假名→查是否日文台词刻意保留；术语命中→查当前语境是否适用术语条件。
4. **账本**：跨会话/多天的大项目在 `polish_state.json` 里记种子清单（pattern + consumed 状态），与已有批次记录并列。
5. **边界**：种子循环是**探查循环**，不是对同一行反复润色——策略一的实测结论"润色只做一轮，越润越差"不变；种子扩大的是**调查范围**，不是单行重润次数。

## 策略零：无 API 校对档（非润色，`scripts/polish/direct_polish.py`）

适用：还没接大模型 API、或想先零成本清洗最明显的机械硬伤。**归类：校对工具**
（与 `tl_check` / `screen_quality` 同族），不属润色——它只修机械硬伤（标点/高频翻译腔），
不碰语义、语气与文风；要"母语级流畅"请走策略一。

机制：对 `game/tl/<lang>/` 全量 say 条目逐条应用正则规则，**绝不碰 `{标签}`、`[插值]`、`%%`、`\n` 转义**，只改译文措辞；每条改写都记入 `direct_report.json`（前后对比+命中规则名），供人工复核。

可执行管线（实测，Dissonance 0.14 schinese）：

```
# 1. 抽条目（锚点与 autotranslate 兼容）
python scripts/polish/extract_say.py game/tl/schinese -o .cache/polish/entries.json

# 2. 零 API 直接润色（默认 --dry-run，只出 JSON 不碰 tl）
python scripts/polish/direct_polish.py game/tl/schinese \
    -o .cache/polish/direct_fixes.json \
    --report .cache/polish/direct_report.json

# 3. 复核 direct_report.json，确认无误后回填（先 --dry-run 预览）
python scripts/translate/autotranslate.py apply game/tl/schinese \
    --input .cache/polish/direct_fixes.json --overwrite --dry-run
python scripts/translate/autotranslate.py apply game/tl/schinese \
    --input .cache/polish/direct_fixes.json --overwrite   # 实写，自动 .bak

# 4. 如需继续交 AI 审稿残留：规则改完后重新抽条目，再切批
python scripts/polish/extract_say.py game/tl/schinese -o .cache/polish/entries.json
python scripts/renpy-tools-cli.py polish --pool .cache/polish/entries.json \
    --tl game/tl/schinese -o .cache/polish/
# 然后按 batch_NNN.prompt.md 让 AI 审稿 → merge_polish.py → autotranslate apply --overwrite
```

> 刻意不提供 `--direct-fixes`（预载改写结果）与 `--auto-screen`（内置筛行）：
> 前者多一次 30s 的抽取就能换掉切批器里的第二份状态，后者让筛行规则多一个维护处。
> 需要时按上面的命令序列走即可。

规则分两组：
- **SAFE**（自动应用，误伤低）：同种中文标点重复→一个；重复半角 `! ?` → 全角单个；半角 `! ? ; :` → 全角（避开 `1,000` 千分位）；多空格→一个；`将会`→`会`；`如果…的话`→`如果…`；连续的的→`的`；`哦我的天`→`天哪`。
- **REVIEW**（`--include-review` 才开启）：`被`+1~4 汉字→去掉`被`；`作为一个`→去掉。这两条有误伤风险，建议先看报告再决定。

边界：只做机械改写，不做语义层意译；角色语气、文风统一、术语漂移仍需策略一的 AI 润色。结构守恒由 `merge_polish.py` 门面把关（与 `direct_polish` 内部自检同口径）。

## 策略二/二B 详情（风格前置 + Agent 审校）

来源：18 万字游戏对白实战（见文末来源①）。关键实测数据：初稿修改率约 75%（200 行改 150+），抽查 99% 的修改为正向改善；**润色只做一轮**——让润色者对自己再润一遍，好坏改动五五开，越润越差。

流程：

1. **切批**：按对话行分批（**约 150 句/批**，实测见「批次大小实测」节：200 偏大、
   100~150 更佳，成本优先可 200），一次只给润色者 2~3 批；批次过大会明显掉质量、
   术语不一致增多。切批与提示词生成已脚本化，见下方 5b 的 `plan_batches.py`。

> 2026-10-06 更新：其**质量判定经验已移植**成本仓库 `scripts/polish/screen_quality.py`（外文残留聚合+豁免、相似度漏翻 Jaccard、免翻清单；出处见该脚本头部注释），用本仓库管线即可获得同款硬性质校，不必为此启动 LG 本体。

1. **风格前置（0 额外 token）**：文本导入 → 翻译指令挂内置风格预设（"文言文风格""文学措辞风格"）或自定义文风 prompt → 重翻。效果等于"翻译时就润"，适合还没翻或愿意重翻的项目。
2. **Agent 审校当润色器（按范围耗 token）**：对其 `item-review` / `page-review` 审校技能下明确指令——"对指定范围按 XX 风格润色，保留术语表条目和占位符"。该技能默认原则是"程序化批量探查优先，仅在无法程序化探查时动用模型"，所以 token 只花在有疑点的条目上；配合其 glossary（术语表）保证一致性。
3. 辅助：其本地质量规则（行数对齐/外语残留/标点/术语命中）零 token，可先跑一遍把可疑行筛出来，再决定润色范围。

局限：Ren'Py tl 文件的支持情况以实际导入为准；`{w}`、`{nw}`、`[变量]` 等 Ren'Py 特有标记的保护必须在自定义指令里写明，不能依赖其通用规则。

## 7. 审稿 vs 机翻矫正：喂什么决定得到什么（2026-10-18，Dissonance 0.14 实测）

策略一早期实现把批次渲染成 `| file:line | 角色 | 原文 | 译文 |` 表格、原文译文一律截断到 90 字、角色设定为「去翻译腔/改口语/修正语法」三件事。实测它做出来的是**机翻矫正**，不是审稿——模型拿不到连贯上下文，只能逐行找茬。

| 问题 | 实测数据 | 后果 |
|------|---------|------|
| 原文截断到 90 字 | 17,485 / 44,387 = **39.4%** 的行原文被砍半 | 读半句判断不了语病，也判断不了衔接 |
| 表格化逐行孤立 | 全部 44,387 行 | 看不到「这句接上一句」，无从谈上下文流畅 |
| 角色=「做三件事」 | 全部批次 | 暗示每行都要改，**违反本文档自己的结论「越润越差」** |
| 跨场景批次 | 612 / 1541 批（40%）混多场景；25,217 条（57%）落在被切碎的 `split` 场景里 | 场景边界被打散，同角色语气连贯性受损 |

**改法（已落地在 `plan_batches.py`）**：

1. **渲染成连续剧本块**：`### 场景：<name>` + `` `file:line` 角色：`` + `原：` / `译：`。模型读到的是一段戏，而不是一堆四元组。
2. **不截断长句**：上限提到 400 字。实测该库最长 orig 仅 200 字出头，**新版零截断**（旧版 39.4%）。
3. **角色改为「中文审稿人」**，显式写入「大部分句子是好的，保持原样」「拿不准就不改」「禁止为了改而改」。
4. **只输出改动行**：判断为「不用改」的不进 `fixes.json`；`merge_polish.py` 另会剔除模型仍输出、但值与旧译文相同的条目（`[跳过]`，回填与否等价，留着只污染 diff 与统计）。

**代价**：prompt 体积 +16.1%（约 236 万 → 274 万 token/全库，按 40 句/批计）。但**输出侧大幅缩减**——若 AI 平均只改 10% 的行，回填量从 44,387 条降到约 4,438 条。净 token 更省，且改的是真正不通顺的地方。

> 补充实测（同库，2026-10-18 复算）：连续同场景段共 3,637 个，最长 223 条（`hallo10`），中位数仅 1 条——这正是「按场景合并相邻场景而非每场景一批」的依据。单场景跨段合计最多的是 `day_six_menu` 449 条。

## 批次大小实测（2026-10-27，Dissonance 0.14 schinese 44,387 条）

对 `plan_batches.py` 的 `--batch-size` 做 100/150/200/300 四档实测（同 entries、同 tl；
跨场景数按 `(file,line) → translate 场景名` 映射统计）：

| batch-size | 批数 | 平均/批 | 中位/批 | 单场景批占比 | 跨 5+ 场景批占比 | 跨 10+ 场景批占比 |
|---|---|---|---|---|---|---|
| 100 | 574 | 77 | 87 | 27% | 37% | **10%** |
| 150 | 384 | 116 | 132 | 19% | 53% | **21%** |
| 200 | 263 | 172 | 184 | 7% | 70% | **37%** |
| 300 | 169 | 263 | 279 | 1% | 88% | **59%** |

- **200 偏大**：37% 的批跨 10+ 场景——AI 读的"一段戏"是碎片拼合，撞上 §7 批评过的
  跨场景问题。省 token 是真的（263 批），上下文连贯性是假的。
- **100 最健康**：跨 10+ 只 10%、单场景批 27%；代价是批数 ×2.2（每批固定上下文开销）。
- **150 是成本/质量平衡点（默认建议）**；300 最差，别用。
- 四档 split 均为 0：本库连续场景段最长 223 条 < 300，不会劈场景；但单场景跨文件段
  可更长（如 `day_six_menu` 跨段合计 449 条），切批时留意。

**结论**：`DEFAULT_BATCH_SIZE` 已从 200 改为 150；追求上下文质量的项目直接用 100。

## 8. 轻度润色无人值守档（2026-10-22，Dissonance 0.14 三批复盘）

> 用户需求："轻度润色只需保持上下文流畅，无需完美精致"。此档 = **AI 端到端替代人工**，
> 接受标准放宽为「读着通顺、事实不错、术语一致」，不追求文学级。

### 三批实测结论（Dissonance 0.14 schinese，约 4.6 万行）

| 发现 | 数据 | 对流程的含义 |
|------|------|-------------|
| AiNiee 精调初翻质量中上 | 单文件抽查修改率仅 **3~8%**（对比 18 万字实战初翻的 75%） | 轻度档的价值不在逐行加工，在**术语统一 + 完整性修复** |
| 术语暗病跨文件 | 活动室/娱乐室 61:19、主事件/主线事件、查看/观看 28:24、Koi Cafe 三种写法 | 一轮全局术语审计 ≈ 十个文件逐行润色的收益 |
| 历史结构损伤隐藏在库里 | 全库引号奇偶扫描抓出 **4 行**损坏（历次 .bak 轮换丢失配对） | AI/人工过稿之前必须先跑完整性检查——这类行不修会显示错乱甚至崩 |
| 半角标点禁入中文正文 | `"透.*"`、`..?` | typography 检查已覆盖，终检别漏 |
| 「您」误报风险 | 学生对老师敬语 219 处全部成立 | **禁止**无脑全局替换,敬语判定靠语境 |
| AI 整理清单时的转码遗漏 | 批 2 计划 53 条实写 51 条(hallo4 两行被吞),靠**抽查落盘行**抓回 | fixes 清单产出后必须 grep 回读核对键数;抽样自审不可省 |

### 无人值守档流程（轻度标准）

1. **完整性先行**(零 token):`tl_check.py` → `fmtlint`（E012 引号奇偶，跨平台，入 `all`）→ `check_typography.py`
2. **全局术语审计**(一轮,非逐文件):`check_duplicate_translations.py` + 关键词扫描
   (场所/称呼/系统词),统一后把术语写进项目根 `翻译结果.md`
3. **AI 剧本块批次**:`plan_batches.py` 切批(按 §7 规范),AI 通读场次,只改真别扭行
4. **回填 + 终检**:`merge_polish.py` 结构守恒 → `autotranslate.py apply --overwrite`
   → 重跑第 1 步确认 0 异常
5. **抽样自审**:每批随机抽 10 行人工级检查(自己抽自查,发现误区即回写本档)

引号奇偶校验已内建为 `fmtlint` 的 **E012**（2026-10-27，剥掉 `\"` 转义后逐行数双引号，奇数即报；跨平台、入 `all`，取代本档曾用的 PowerShell 一行命令）。该 4 行历史损伤形态即 E012 的靶子：`old`/`new` 行由 E001 精确判定，say 行形式（注释+译文行）只有 E012 抓得到。

### 翻译腔规则(已入 screen_suspicious.py RULES,2026-10-22)

三批复盘提炼的高频硬译,权重 1(只作找别扭用,不直接判违规):
`假设[一它这那你我]`、`对此[，。]`、`总而言之`、`(?<!，)不是吗[？?]`(不留逗号变体)。

### 人工保留职责(轻度档仍有必要)

- **风格定调**:整部作品的语气(如"轻小说腔 vs 中性书面")需人拍板
- **尺度把控**:H 场景/俚俗表达的度,AI 按上下文保守处理,重定调再升级
- **全库级决策**:如统一改"前辈→先辈"这类涉及人称关系的取舍

## 9. 并行扇出可选档（2026-10-27，仅用户嫌慢时启用，不做默认）

44k 行、300+ 批的库串行审稿慢。术语表冻结 + `context.md` 章节核心产出**之后**，批次之间其实是独立的——这是能并行的前提，也是它的代价来源：

- **能并行**：各批只依赖全局语境（术语表 + 章节核心），不依赖其他批的产出
- **丢掉的东西**：串行批次提示词里的「上一批已定术语」接缝。并行时改为把**冻结后的完整术语表全量前置**进每批 prompt，替代增量衔接
- **不变的东西**：连续剧本块渲染（§7 规范）、只输出改动行、`merge_polish` 结构守恒门、`apply` 安全网、只润一轮

做法：把 `batch_NNN.prompt.md` 分发给并行子代理（各批独立上下文，正好满足「审稿角色不与翻译者混用」），各批产出 fixes 后仍走统一的 `merge_polish.py` → `apply`。并发度以术语表覆盖度为界：术语表越全，批间串戏风险越低；专名密集的项目保守用低并发。

> 不默认并行：串行 + 上一批术语接缝是实测出来的质量路线；并行是拿一点一致性风险换墙钟时间，由用户拍板。
